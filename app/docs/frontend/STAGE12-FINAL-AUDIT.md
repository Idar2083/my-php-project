## Оценка полной идемпотентности — без частичной реализации

У текущего API нет гарантии повторного успешного ответа на тот же запрос.
Если пользователь заново наполнит корзину между потерянным ответом и старым
повтором POST, сервер не отличит старый повтор от нового намеренного оформления.
UI предупреждает о проверке истории и не выполняет автоматических повторов.
Поэтому существующая защита достаточна для проверенного сценария потребления
неизменной корзины, но не для гарантии exactly-once произвольных повторов.

Минимальное совместимое расширение при принятии такого требования:

* опциональный заголовок Idempotency-Key с валидируемым UUID; старые клиенты без
  ключа сохраняют нынешний контракт;
* nullable checkout_key и хеш нормализованного входного адреса в orders,
  уникальный индекс (user_id, checkout_key) через новую миграцию; старые строки
  без ключа не меняются;
* lookup/возврат прежнего заказа до проверки пустой корзины и транзакционная
  обработка гонки уникальности; несовпадение payload у того же ключа — 409;
* клиент сохраняет один ключ для одного checkout attempt в памяти, в том числе
  при таймауте, и создаёт новый только для нового намеренного оформления;
* определить срок хранения/правила повторов и ответ при изменившемся статусе;
  проверить параллельные повторы, потерю ответа, новое содержимое корзины,
  конфликт payload, другой user и старые клиенты без ключа.

Это оценка, не внедрённый контракт. Миграций, колонок, заголовков или частично
работающего middleware в текущем этапе нет. Перед автоматическими повторами,
платежами или требованием восстановления подтверждения после timeout нужен
отдельно согласованный и полностью проверенный механизм.
