# Покупательский интерфейс и обработка заказов

## Реализовано

Существующий Vue 3/Vite frontend расширен без новых зависимостей. Каталог вынесен
в Catalog.vue с сохранением обработки загрузки, ошибок, пустого списка,
таймаутов, пагинации и восстановления удалённой последней страницы. Добавление
товара отправляет product_id/quantity в реальную серверную корзину. Гость сначала
входит; несохранённое намерение добавить один товар живёт только в памяти вкладки.
Гостевая серверная корзина не имитируется.

Регистрация и вход используют POST /register и /login, затем GET /me. Роль берётся
из /me, JWT не декодируется для назначения прав. Токен хранится только в памяти,
передаётся Authorization: Bearer и исключён из localStorage/sessionStorage/URL.
После обновления вкладки нужен повторный вход; серверная корзина сохраняется.
Пароль очищается после запроса. Повторная отправка блокируется до проверки /me.
401 приватного запроса закрывает локальную сессию. Logout вызывает POST /logout,
после чего токен удаляется даже при сетевой ошибке, с явным сообщением об отсутствии
подтверждения отзыва. Поздний ответ предыдущей сессии отбрасывается.

Корзина читает GET /cart, меняет количество через PUT /cart/items/{itemId},
удаляет через DELETE. Показывает текущую сумму и ошибки ограничений категорий.
Форма оформления передаёт только восемь разрешённых полей: region, city, street,
house, apartment, entrance, postal_code, delivery_method. Цены/пользователь/статус не отправляются.
POST /orders определяет итог на сервере. Двойная отправка во время ожидания
блокируется; автоматических повторов нет. При неясном сетевом исходе предлагается
сначала история заказов. Успех показывает серверный ID и сумму, затем историю
с опциональной пагинацией; повтор без изменения корзины отклоняется после её
атомарной очистки. Параллельное оформление одной корзины проверено отдельными процессами.
Есть детали собственного заказа с сохранённым названием товара и ценой покупки.

Администратор получает общий список с пагинацией по 30 и детали: покупатель,
состав, сумма, адрес, дата и статус. UI показывает только allowed_statuses,
полученные от backend. После изменения статуса перечитывает детали. Закрытый
заказ не предлагает изменений. Ошибки 403/404/409 и ошибки сервиса отображаются
без устаревших деталей. Доступ к административному представлению проверяется
по профилю, а реальные права — сервером на каждом запросе.

## Минимальное расширение Order API

Добавлены GET /api/admin/orders?page=1 и GET /api/admin/orders/{orderId}
в существующей группе auth:api + admin. Сервис загружает связанные данные,
контроллер остаётся тонким; новый Form Request ограничивает page 1..1000000.
AdminOrderResource добавляет customer {id,name,email} и allowed_statuses.
Пароль, remember_token и роль покупателя не сериализуются. Покупательские
GET /orders и /orders/{orderId} сохраняют фильтрацию по владельцу.
Финальная доводка добавляет опциональную пагинацию GET /orders?page=N; без page
контракт коллекции сохранён, с page возвращаются стандартные Laravel links/meta.
OrderItemResource дополнен product_name из существующего снимка order_items,
чтобы переименование товара в каталоге не меняло историческое название заказа.
Это добавочные поля/маршруты, старые контракты сохранены. Миграций нет.

Правила смены статуса не ужесточались: существующий сервис принимает любой
OrderStatus из незакрытого заказа, в том числе paid. completed и cancelled
терминальны. UI исключает текущий статус как бессмысленную операцию, остальные
варианты отражают реальный backend; paid подписан как ручная отметка, не платёж.

## Сохранённые ограничения и задачи перед запуском

* Нет онлайн-оплаты и интеграции платёжного шлюза.
* API требует адрес для delivery/pickup/courier; для самовывоза форма тоже требует
  адрес. Пункт самовывоза и расписание API не предоставляет, UI их не выдумывает.
* API не возвращает валюту. Суммы показываются как в существующем контракте,
  без выдуманной валюты. Перед запуском нужно согласовать валюту/единицы веса.
* После финальной доводки история покупателя пагинируется по 30 при явном
  `GET /orders?page=N`. Без `page` сохранён прежний ответ со всеми своими заказами.
* Переходы статусов широкие; строгая последовательность, возвраты и права
  отдельных операторов требуют отдельного бизнес-решения.
* Блокировка кнопки не заменяет серверную идемпотентность оформления. При потере
  ответа нужно проверить историю; idempotency key этот API не поддерживает.
* Навигация — представления в текущем Vue-приложении, без новой router-библиотеки.
  Отдельных постоянных URL/восстановления выбранного представления после reload нет.
* Нет восстановления пароля и постоянной сессии между перезагрузками.
* Нужны браузерные проверки мобильной вёрстки, клавиатуры, нативной валидации,
  автозаполнения и поведения при потере сети. jsdom не подтверждает эти свойства.
* Операционные задачи предыдущего этапа (proxy, общие cache/blacklist, ограниченные
  MinIO-ключи, проверка целевого окружения) остаются. Production не проверялся.

## Проверки и воспроизведение

Обычные команды: `npm test --prefix frontend`, `npm run build --prefix frontend`.
Старые 44 теста каталога сохранены: App.test.js теперь монтирует выделенный
Catalog.vue, новые тесты App и сценариев находятся в shop.test.js/auth.test.js.

Для настоящего API используется отдельная временная Docker-сеть pizza-ui-isolated,
PostgreSQL 15 с двумя БД: pizza_app_test для PHPUnit, pizza_ui_test для HTTP UI.
RabbitMQ, Redis, MinIO также отдельные, без development-томов/публичных портов.
Временный Laravel server публикуется только на случайном 127.0.0.1-порту.
PHPUnit использует array cache, HTTP UI — database cache своей pizza_ui_test,
чтобы лимитер и отзыв JWT действовали между настоящими HTTP-запросами.

Тестовые данные создаёт tests/Support/ui_api_fixture.php; он требует APP_ENV=testing,
DB_DATABASE=pizza_ui_test и UI_API_FIXTURE=1. Входной UI_TEST_ADMIN_PASSWORD
создаётся случайно и передаётся через окружение, не хранится в репозитории.
Скрипт предназначен исключительно для новой изолированной БД после миграций.
Существующие записи приложения он не использовал.

Запуск реального UI/API теста: передать UI_API_URL=http://127.0.0.1:<порт>
и UI_TEST_ADMIN_PASSWORD из временной среды, затем в frontend выполнить
`npm test -- tests/purchase.integration.test.js`. Без этих переменных тест
явно пропускается. Он использует настоящий fetch и Vue/jsdom, без подмены HTTP
ответов: каталог → регистрация → добавление → изменение количества → заказ →
собственные детали → выход → вход администратора → общий список/покупатель →
in_process → completed → повторный вход покупателя → завершённый заказ.
Дополнительно проверяет 403 для buyer на admin API и 401 для отозванного JWT.
Это интеграционный тест UI/API, не браузерный E2E.
